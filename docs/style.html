§ 1Tres principios

Toda regla de este documento se deriva de tres frases. Si una regla futura las contradice, gana la frase.

Principio 1

El código dice qué. El comentario dice por qué.

Un comentario que se puede borrar sin perder información es ruido con costo de mantenimiento: envejece, miente y nadie lo actualiza. Si hace falta un párrafo para explicar qué hace una función, el arreglo es la función, no el párrafo.

Principio 2

La documentación de API y el comentario de implementación son cosas distintas, con lectores distintos.

/// y //! los lee quien usa el código sin abrirlo: describen contrato, invariantes, panics y seguridad. // lo lee quien mantiene el código con el archivo abierto: describe la decisión no obvia que tomó la línea de abajo.

Principio 3

Una regla sin herramienta que la haga cumplir es una intención, no una regla.

Cada sección termina diciendo qué la verifica. Cuando no existe herramienta, se dice, y esa regla pasa a la revisión manual del §10 — no se finge que está cubierta.

§ 2Comentarios

Eje 2.1

Documentación vs. implementación

Decisión

/// en todo item público. Primera línea: una oración, en imperativo o descriptiva, que cabe en una línea. Si hace falta más, va en un párrafo aparte después de una línea en blanco.

El motivo no es estético: rustdoc renderiza el primer párrafo en la tabla de items del módulo, junto al nombre. Un primer párrafo de seis líneas rompe esa tabla.

No

/// Costuras: attach vértice↔vértice inter-pieza
/// con rest 0 (ADR §2.3). Conjunto GLOBAL del
/// solver, con dueño e indexación propios — los
/// pares referencian índices del estado combinado
/// de todas las piezas.
pub struct Seams { .. }

Sí

/// Vertex-to-vertex seam attachments, rest length 0.
///
/// Indices are global across all pieces: they address
/// the combined solver state, not a single piece.
pub struct Seams { .. }

La segunda versión dice lo mismo en menos, y la única frase que un consumidor no puede deducir de las firmas — que los índices son globales — queda sola, donde se ve.

Comentarios de implementación

Un // justifica una decisión que un lector competente cuestionaría.

Buenos candidatos: por qué una constante vale eso y no otra cosa, por qué el orden importa, qué pasa si borrás la línea, qué se intentó antes y falló. Malos candidatos: repetir el nombre de la función en prosa.

El repo ya tiene ejemplos del comentario correcto. Este es el mejor que hay hoy, y sobrevive traducido tal cual:

// A kinetic-damping zero leaves v=0 without the cloth being at
// equilibrium, so sleep needs consecutive quiet ticks, not one.
let mut quiet_ticks = 0u32;

Nadie deduce eso leyendo quiet_ticks. Ese comentario se gana su lugar.

Eje 2.2

Lo que nunca va en un comentario

  • Procedencia. (issue #21), Spike 4 (issue #36), lección de Blender. Eso lo responde git log -S y git blame con más precisión y sin envejecer. El issue se cierra; el archivo sigue ahí con la referencia muerta.
  • Punteros a documentos renumerables. ver docs/architecture.html §2.4 apunta a una numeración que cambia cuando el ADR se edita. Si el vínculo es esencial, nombrá el concepto (see ADR: incremental derivation), no el número.
  • Reglas que ya viven donde se hacen cumplir. «Solo importa toile-engine» está en Cargo.toml, que es donde el compilador la aplica. Repetida en un comentario, se desincroniza en silencio.
  • Narración de la estructura del archivo. «Izquierda el patrón 2D, derecha el 3D» describe dos funciones que están veinte líneas abajo y se llaman pattern_panel y viewport_panel.
  • Estado temporal. «primera implementación», «por ahora», «el spike decide si…». Eso es una tarea, y las tareas van al tracker.
Sí van

Separadores de sección en archivos largos, en una línea, con el ancho del archivo. El repo ya usa este formato y se queda:

// ── linear algebra (column-major) ─────────────────────────
Eje 2.3

El caso //!

El doc de módulo no es malo por definición — es malo casi siempre porque se usa como lugar donde narrar. Hay exactamente un caso donde gana su lugar.

Decisión

Un //! por crate, en su lib.rs, y documenta el invariante que el consumidor no puede deducir de las firmas. Máximo cuatro líneas.

Ese es el front page de rustdoc: lo primero que ve alguien que llega al crate desde docs.rs. Es el único comentario del repo con audiencia externa real.

Descartado

//! en binarios (main.rs) y en módulos internos. Rustdoc no los publica: el único lector posible ya abrió el archivo y tiene el código delante. Si el módulo necesita explicación para entenderse, el problema es el módulo.

El ejemplo que motivó este documento, y su reescritura:

No — toile-app/src/main.rs

//! Cliente de escritorio — la vista split (issue #21).
//!
//! Izquierda: el patrón 2D con puntos de control arrastrables (vía A en
//! vivo). Derecha: la tela drapeada por el renderer wgpu propio (módulo
//! `render`, ADR §2.6) — offscreen con depth buffer, sombreado suave con
//! las normales que publica el hilo de sim. Solo importa `toile-engine`.

Sí

mod render;

Seis líneas a cero. Todo lo que decían está en el código o en Cargo.toml, salvo una cosa que no estaba en ningún lado y que sí merece un comentario — pero abajo, pegada a la línea que la necesita:

// The sim thread advances on its own clock; without this the
// viewport only redraws on input events.
ui.ctx().request_repaint();

Y la versión buena de un //! de crate, sobre el mismo material:

No — toile-sim/src/lib.rs, 9 líneas

//! Solver de tela XPBD small-steps residente.
//!
//! Buffers SoA, coloreo de grafo determinista,
//! anisotropía urdimbre/trama, costuras
//! inter-pieza globales, colisión por SDF,
//! kinetic damping y sleep por islas de
//! acoplamiento. El solver nunca se resetea: los
//! cambios de forma llegan como nuevo estado de
//! reposo (hot-swap entre substeps).

Sí — 3 líneas

//! Resident XPBD cloth solver.
//!
//! The solver is never reset. Shape edits arrive as
//! new rest values and are hot-swapped between
//! substeps, preserving positions and velocities.

La lista de features se lee sola en la lista de items que rustdoc pone justo debajo. El invariante «nunca se resetea» no se lee en ningún lado, y es lo único que un consumidor tiene que saber antes de tocar la API.

Verificado por

clippy::too_long_first_doc_paragraph (estable desde 1.82) para el primer párrafo. El límite de líneas del //! y la prohibición de procedencia no tienen lint: script propio (§9) y revisión manual.

§ 3Idioma

Decisión

Código en inglés. Documentación de producto en español.

Inglés: identificadores, comentarios, doc comments, mensajes de commit, mensajes de panic/expect, nombres de tests, etiquetas de debug.

Español: README.md, docs/*.html, issues, y los textos que ve el usuario en la UI.

Dos razones, ninguna de gusto personal:

  1. El código ya está en inglés y los comentarios no. boundary_fracs, pair_seam, transfer_state, strain_limit conviven con «el aro de una prenda cerrada se elonga bajo su peso». Un archivo bilingüe obliga a cambiar de idioma cada tres líneas: es la peor de las dos opciones, peor que cualquiera de las dos puras.
  2. Toile es open source y busca contribuciones. El ADR nombra el bus factor de un solo desarrollador como riesgo #5 y propone «motor headless + CLI + formato abierto para que el proyecto sobreviva a su GUI y a su autor». Comentarios en español cierran esa puerta a la mayoría de quienes podrían cruzarla.
Glosario de dominio

El patronaje tiene vocabulario técnico propio en ambos idiomas. En código se usa el término inglés estándar, siempre el mismo:

§ 4Estructura y modularización

Eje 4.1

Nombres

Se sigue Rust API Guidelines sin excepciones locales. Los puntos que este repo va a tocar seguido:

  • C-CASE — snake_case para funciones y módulos, UpperCamelCase para tipos, SCREAMING_SNAKE para constantes.
  • C-CONV — as_ (préstamo barato), to_ (conversión cara), into_ (consume). No se mezclan.
  • C-GETTER — el getter se llama contour(), no get_contour().
  • C-CTOR — el constructor es new; las variantes describen su diferencia (from_contour, with_capacity).
  • C-COMMON-TRAITS — todo tipo público deriva Debug. Clone/Copy/Default cuando tengan sentido.
  • C-CUSTOM-TYPE — un bool en una firma no dice qué significa. build_and_drape(dx, dz, true) no se entiende en el sitio de llamada; un enum de dos variantes sí.
Eje 4.2

Límites de tamaño

Decisión

Archivo: 300 líneas. Función: 60 líneas como objetivo, 100 como límite duro.

No es una regla estética. Un archivo que no entra en la cabeza de una persona tampoco entra en la ventana de atención de quien lo revisa — humano o agente — y lo que sigue es exactamente lo que le pasó a este repo: cinco copias de la misma escena dentro de un mismo archivo, porque nadie veía las otras cuatro.

El límite se aplica al archivo, no al concepto: si un concepto necesita más de 300 líneas, se parte en submódulos, no se le sube el límite.

Eje 4.3

Cómo se parte

Por concepto, nunca por longitud

Partir un archivo de 1.200 líneas en cuatro de 300 no arregla nada si los cuatro siguen hablando de lo mismo. La prueba: cada módulo tiene que poder describirse en una frase sin la palabra «y».

Si la frase necesita un «y», ahí está la línea de corte.

Fachada

Cuando el módulo ya tiene consumidores, se parte hacia adentro: foo.rs pasa a declarar sus submódulos y re-exportar lo público. Los call sites no cambian, y el refactor se puede verificar contra el golden sin tocar una sola línea fuera del crate.

// toile-sim/src/xpbd.rs — la fachada, no la implementación
mod color;
mod contact;
mod damping;
mod metrics;
mod normals;
mod parallel;
mod ptr;
mod sdf;
mod simd;
mod solver;
mod state;

pub use color::{ColoredConstraints, color_constraints};
pub use damping::{KineticDamper, zero_velocities};
pub use metrics::{kinetic_energy, max_speed, position_hash};
pub use normals::vertex_normals;
pub use parallel::substep_colored;
pub use sdf::SdfGrid;
pub use simd::substep_colored_simd;
pub use solver::substep;
pub use state::{DistanceConstraints, Seams, State};

Así quedó el repo al aplicar la regla. Ningún archivo pasó de 300 líneas y el golden no se movió ni un bit en todo el proceso:

AntesLíneasDespués

toile-sim/xpbd.rs784fachada + state · sdf · contact · solver · color · ptr · parallel · simd · damping · metrics · normals

Partir por concepto tuvo un efecto que partir por longitud no habría tenido: al aislar la resolución de contacto en su propio módulo apareció que estaba escrita tres veces —escalar, paralela y SIMD— y las tres colapsaron en una sola función, bit por bit idéntica.

Un módulo es un concepto

No una fase del proyecto ni un experimento. Nada se llama spike, v2, new_, tmp, utils ni helpers: esos cuatro nombres son un contenedor sin criterio, y todo lo que cae adentro deja de tener dueño.

Layout: foo.rs junto a foo/ para los submódulos. No se usan mod.rs.

Eje 4.4

Fixtures

Decisión

Una escena de prueba se define una vez y se importa. Si un literal aparece en dos archivos, ya es un fixture disfrazado y sube a su crate.

Es la regla que más deuda paga en este repo. La escena del corpiño —contorno, centroide, altura de suelta, SDF del avatar— estaba copiada en cinco archivos: cualquier cambio de la escena exigía encontrar las cinco, y el día que alguien encontrara cuatro, el golden se rompería sin que nadie supiera por qué.

Verificado por

clippy::too_many_lines para funciones, y el script propio para el límite de archivo. La duplicación de fixtures sigue siendo revisión manual (§10).

§ 5Errores, panics y validación

Decisión

Los crates de librería devuelven Result. Solo los binarios hacen unwrap/expect.

Tipos de error con thiserror en la librería, anyhow en toile-cli y toile-app. Ambos ya están presupuestados en el ADR §2.8.

Un expect en una librería convierte un dato de entrada malo en un crash del proceso del usuario. cdt::triangulate hace hoy .expect("vértice inválido"): un contorno con un NaN—perfectamente alcanzable desde un arrastre en la UI— mata la aplicación entera.

Excepción

expect es correcto para un invariante que el propio código garantiza. El mensaje explica el invariante, no el síntoma:

// no:  .expect("vértice inválido")
// sí:  .expect("contour was validated as finite by Piece::new")
Aserciones en el camino caliente

debug_assert! para invariantes de solver que costaría verificar en release. assert! solo cuando continuar corrompería datos en silencio — como el assert!(col < 64) del coloreo de grafo, que está bien donde está.

Verificado por

clippy::missing_panics_doc (documenta los panics que quedan) y clippy::missing_errors_doc. unwrap_used/expect_used se activan por crate de librería, no en el workspace.

§ 6unsafe

Esta es la excepción explícita al minimalismo del §2: en unsafe, el comentario es obligatorio y la extensión no se penaliza. Es el único lugar del repo donde la prosa es parte del contrato de corrección.

Decisión
  • unsafe fn lleva sección # Safety en su doc, con las precondiciones que el llamador debe garantizar.
  • Todo bloque unsafe lleva un comentario // SAFETY: inmediatamente arriba, que explica por qué las precondiciones se cumplen acá.
  • Una operación insegura por bloque. Un bloque que envuelve doce derefs no documenta ninguno.
  • unsafe_op_in_unsafe_fn en deny: dentro de una unsafe fn, cada operación insegura sigue necesitando su bloque.

El patrón Ptr(*mut f32) de xpbd.rs es el caso crítico del repo: su corrección depende por completo de una propiedad que el compilador no ve —que dentro de un color ningún par de constraints comparte vértice— y hoy son 13 bloques sin // SAFETY:. Es exactamente donde el comentario largo se justifica.

Verificado por

clippy::missing_safety_doc (default), clippy::undocumented_unsafe_blocks, clippy::multiple_unsafe_ops_per_block, unsafe_op_in_unsafe_fn.

§ 7Determinismo — reglas duras

Toile promete que el mismo archivo produce el mismo drapeado, bit a bit, en ARM y en x86. Esa promesa se rompe con un cambio de una línea que en cualquier otro proyecto sería inocente. Estas reglas no son estilo: violarlas es un bug.

Reglas
  • Nunca iterar un HashMap/HashSet cuando el orden influya en el resultado. BTreeMap, o Vec con orden canónico explícito.
  • Orden total y canónico en todo sort que alimente al solver: la clave incluye un desempate por índice. sort_by_key(|i| (min_vertex, i)), nunca sort_unstable_by sobre una clave con empates.
  • El inner loop se limita a + − × ÷ sqrt en f32. Transcendentales solo vía libm, y fuera del camino caliente.
  • Sin fast-math, sin FMA implícito, sin reordenar expresiones de punto flotante «porque es equivalente»: en IEEE no lo es.
  • Sin paralelismo oportunista sobre floats. El work-stealing es incompatible con el determinismo: el paralelismo entra solo por coloreo con escrituras disjuntas.
  • Un cambio de física cambia el golden. Se regenera con cargo run -p toile-cli -- drape y se actualiza la constante en el mismo commit, con el porqué en el mensaje. Un golden actualizado sin justificación en el mensaje se rechaza en review.
Paridad entre caminos del solver

Si existe más de una implementación del mismo substep (escalar, coloreada, SIMD), todas soportan el mismo conjunto de features o el que no lo hace se marca en su tipo, no en un comentario. Un camino paralelo que ignora en silencio las costuras produce física distinta con la misma firma.

Verificado por

El golden de tests/golden.rs corriendo en macOS ARM y Linux x86 contra la misma constante. Es la única verificación automática; el resto de las reglas es revisión manual, y son las primeras que un agente viola.

§ 8Tests

Decisión
  • Toda función pura de toile-geom y toile-mesh lleva unit tests en su archivo, en #[cfg(test)] mod tests.
  • cargo test --workspace tiene que fallar si alguien rompe algo. Durante toda la fase de exploración no falló nunca, porque el único test del repo estaba #[ignore]: hoy son 24 y corren en cada PR.
  • #[ignore] se reserva para goldens que exigen --release, y CI los corre explícitamente.
  • Los casos borde se testean antes que el camino feliz: contorno vacío, dos puntos iguales, count < 2, NaN de entrada.
  • Nombre del test: lo_que_se_espera, no test_foo. sample_closed_wraps_at_full_perimeter.
Verificado por

CI. Cobertura no se mide ni se persigue como número.

9.1

La decisión de nightly

Decisión

rustfmt.toml declara las opciones inestables y CI corre cargo +nightly fmt --check. El build sigue siendo 100% estable: nightly se usa solo para formatear, que no afecta al binario.

# rustfmt.toml
edition = "2024"
style_edition = "2024"
max_width = 100

# nightly-only: sin esto rustfmt no toca los comentarios
unstable_features = true
wrap_comments = true
comment_width = 80
format_code_in_doc_comments = true
imports_granularity = "Module"
group_imports = "StdExternalCrate"
Alternativa descartada

Quedarse en estable puro y no verificar comentarios. Era el estado del repo cuando se escribió este documento, y la razón por la que existe.

9.2

Lints del workspace

Los lints se declaran una vez en el Cargo.toml raíz —estable desde Rust 1.74— y cada crate hereda con [lints] workspace = true. Los valores de abajo salen de correr clippy::pedantic sobre el repo: 1.415 avisos, de los cuales 788 son indexing_slicing. Indexar es el idioma de un solver SoA, no un olor; se permite explícitamente en vez de dejar que ahogue todo lo demás.

# Cargo.toml (raíz) — cada crate hereda con `[lints] workspace = true`
[workspace.lints.rust]
missing_docs = "warn"
unsafe_op_in_unsafe_fn = "deny"

[workspace.lints.clippy]
# priority = -1 so the individual allows below win over the group.
pedantic = { level = "warn", priority = -1 }

# Numeric code: indexing and narrowing casts are the idiom here, not a smell.
cast_possible_truncation = "allow"
cast_precision_loss = "allow"
cast_possible_wrap = "allow"
cast_sign_loss = "allow"
indexing_slicing = "allow"
many_single_char_names = "allow"
must_use_candidate = "allow"
similar_names = "allow"

# One SAFETY comment covers a whole phase of identical indexed writes here;
# splitting a nine-deref expression into nine blocks would document less.
multiple_unsafe_ops_per_block = "allow"
# Deliberate on the tiny accessors inside the solver's hot loop.
inline_always = "allow"

# The rules this project actually wants enforced.
too_long_first_doc_paragraph = "warn"
too_many_lines = "warn"
undocumented_unsafe_blocks = "warn"
9.3

Lo que ninguna herramienta cubre

Ni clippy ni rustfmt saben qué idioma hablás ni cuántas líneas debería tener un //!. Para eso hay tres caminos, de menos a más:

Script en CI tools/check-style.sh elegido

Cuatro reglas: idioma, //! fuera de sitio o demasiado largo, procedencia, y tamaño de archivo. Solo grep y find, así que no hay nada que instalar en CI.

ast-grep reglas YAML sobre el AST no v1

Más preciso que grep y con autofix, pero es otra dependencia binaria para tres reglas.

dylint lints de rustc propios no v1

La solución correcta a gran escala: lints reales, con acceso al HIR. Desproporcionado para un repo de 3.700 líneas.

#!/usr/bin/env bash
# Project rules that neither rustfmt nor clippy can see (docs/style.html).
# Uses only grep and find, so it runs anywhere CI puts a shell.
set -uo pipefail
cd "$(dirname "$0")/.."
export LC_ALL=en_US.UTF-8
fail=0
say() { printf '\033[31m✗ %s\033[0m\n' "$1"; fail=1; }

COMMENT='^[[:space:]]*(//|///|//!)'
WORD='(^|[^[:alnum:]])(que|para|los|las|una|este|esta|como|pero|porque|cuando|donde|desde|hasta|entre)([^[:alnum:]]|$)'

# 1. Comments go in English. Spanish diacritics and inverted punctuation are
#    unambiguous; a short stop-word list catches the unaccented rest. Plain
#    non-ASCII is NOT an error: em dashes and multiplication signs belong in
#    English prose too.
if grep -rnE --include='*.rs' "$COMMENT.*([áéíóúñÁÉÍÓÚÑ¿¡]|$WORD)" crates; then
  say "comentarios en español: el código va en inglés (§3)"
fi

# 2. A module doc belongs on a crate root, and stays short.
for f in $(grep -rlE --include='*.rs' '^//!' crates); do
  n=$(grep -c '^//!' "$f")
  case "$f" in
    */src/lib.rs) [ "$n" -gt 4 ] && say "$f: doc de crate de $n líneas (máx 4) (§2.3)" ;;
    *)            say "$f: //! fuera de un lib.rs (§2.3)" ;;
  esac
done

# 3. Provenance belongs in the commit message, not the source.
if grep -rnE --include='*.rs' "$COMMENT.*(issue #[0-9]|[Ss]pike [0-9]|§)" crates; then
  say "procedencia en comentarios: eso va en el mensaje de commit (§2.2)"
fi

# 4. File size limit.
for f in $(find crates -name '*.rs'); do
  n=$(wc -l < "$f")
  [ "$n" -gt 300 ] && say "$f: $n líneas (máx 300) (§4.2)"
done

[ $fail -eq 0 ] && echo "✓ estilo"
exit $fail

§ 10Checklist de PR

Lo que las herramientas no verifican, y por lo tanto hay que mirar a ojo antes de mergear:

  1. ¿Algún comentario nuevo sobreviviría a borrarlo? Si sí, borralo.
  2. ¿Hay un literal que aparece en dos archivos? Es un fixture: subilo a su crate.
  3. ¿El cambio toca la física? Entonces el golden cambió: regeneralo en este commit y justificá el porqué en el mensaje.
  4. ¿Se agregó un camino de solver? Tiene que soportar las mismas features que los demás, o declararlo en el tipo.
  5. ¿Hay un unsafe nuevo? # Safety en la firma, // SAFETY: en el bloque, una operación por bloque.
  6. ¿Hay un expect nuevo en una librería? Debería ser un Result.
  7. ¿Se ordenó algo que alimenta al solver? La clave tiene que ser un orden total, con desempate por índice.
